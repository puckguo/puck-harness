Agent Harness 横向对比讲解

pi · OpenAI Codex CLI · DeepSeek Harness (dsh) · puck agent harness —— 四种设计哲学的正面交锋。数据基于 2026-08 本地源码树实测统计。

一图看懂：四个 harness 的定位

pi

分层复用派

“General-purpose agent with transport abstraction” —— 从统一 LLM API 到可自扩展编码代理的全链路开源库。

TS monorepo多 provider库优先
codex

工业沙箱派

OpenAI 出品。Rust 核心 + 审批策略 + 多级沙箱 + 云任务，经海量真实使用锤炼的生产级编码代理。

Rust + TS SDK进程隔离安全优先
dsh

插件生态派

DeepSeek 出品。“Everything is a plugin”，基于 Cordis 框架，会话日志是唯一事实，Web UI 与 headless 同源。

Cordis 插件日志即事实Web UI

自研 harness：核心 ~700 行零依赖，不需要的功能直接删目录，mock 剧本离线调试，自带计时观测。

逐个讲解：优点与缺点

pi

pi — 分层复用派

值得学的：

  • StreamFn 单一接缝：loop 只认一个函数签名，10 种 provider 协议全部压在接缝后面 —— 本项目 puck 直接继承此设计
  • 纯函数 loop + 薄状态包装：调试可直接调 runAgentLoop，不碰状态机
  • 边界处理细致：length 截断时拒绝执行工具调用（参数可能不完整）、上下文压缩的 prefix 缓存、steering 队列
  • 供应链硬化：精确版本锁定、审计、shrinkwrap —— 开源 agent 的安全范本

代价与短板：

  • provider 矩阵维护成本高：10 种 wire 协议 + 各家 OAuth 流程，个人项目难以跟进
  • 消息模型带 provider 泄漏字段（textSignature / rawStopReason…），通用性打折
  • EventStream 泛型类 + typebox schema 依赖：为通用性引入抽象税
codex

OpenAI Codex CLI — 工业沙箱派

值得学的：

  • Thread / Turn / Item 事件分层：事件模型命名与语义是行业最清晰的，puck 的事件协议直接参考
  • SDK 易用性标准：thread.run() 一次拿 finalResponse + items，90% 场景零样板 —— puck 的 puck.run() 同款理念
  • 安全分层：审批策略 + 多级沙箱 + 工作区信任度，生产环境真正敢放权
  • 进程边界即 ABI：SDK 与核心跨版本解耦，Rust 核心性能与内存安全

代价与短板：

  • 跨进程调试：SDK 问题要在 stdin/stdout JSONL 边界两侧同时看，远比进程内库难
  • 工程体系重：Rust + Bazel + ~90 crates，二次开发门槛极高
  • 宿主必须携带 CLI 二进制；SDK 本质是包装器而非可嵌入运行时
dsh

DeepSeek Harness — 插件生态派

值得学的：

  • “日志即事实”：模型可见的一切必须能从追加式 SessionEvent 日志重建 —— 换 provider / 回放 / fork 全部免费获得。puck 的 session 设计直接继承
  • canonical transcript 与 LLM view 分离（deriveMessages）：压缩/投影永不破坏原始历史
  • 能力接缝：文件系统/子进程/终端共享同一执行世界，指向远程沙箱时整套工具无需改动整体迁移
  • 插件可逆副作用：卸载即回滚，生态可组合性最强

代价与短板：

  • Cordis 学习曲线陡：ctx 注入、waterfall 事件、scope 生命周期 —— 任何一行代码背后都是插件解析链，调试成本高
  • 开发者预览期，明示会有破坏性变更
  • “一切皆插件”的间接层在热路径上带来理解与性能双重开销
puck

puck — 极简裁切派（本项目）

独有优势：

  • 目录 = 裁切单位：不要多 agent？删 subagent 目录。不要持久化？删 session 包。构建依然通过 —— 比“运行时卸载插件”更彻底、更零成本
  • 零外部依赖：出问题全部代码可断点，无 node_modules 黑盒；供应链风险≈0
  • mock 剧本 provider：确定性复现多轮工具流，CI 零网络，bug 复现只需 transcript + 脚本
  • 计时观测（独有功能）：每轮 TTFT / 时长 / tok-s 自动入账，自包含 HTML dashboard + LLM 用时合理性分析，四个 harness 中唯一内建
  • 真实接入即战斗：MiniMax-M3 <think> 内联思考剥离、错误后 steering 恢复、运行中切模型等边界全部实测修复

诚实的短板：

  • 生态为零：无扩展市场、无第三方插件、单一维护者
  • 能力覆盖窄：无 MCP、无 OAuth（订阅制登录不可用）、无沙箱/审批沙箱分层、无 Web UI、无结构化输出
  • provider 协议只有 2 种（OpenAI 兼容 / Anthropic）+ mock；遇到私有协议要自己写 adapter
  • 年轻：未经大规模生产锤炼，边界情况存量远多于三个前辈

puck 的血统 每个设计决策的出处

从 pi 继承

  • StreamFn 单一接缝 ← pi-ai 的核心洞察
  • 纯函数 loop + Agent 状态包装的分层
  • beforeToolCall / afterToolCall 钩子形态
  • length 截断拒绝执行工具调用的边界处理
  • /login 的三层结构（UI 回调 / 编排 / 存储）与 key 优先级链

从 Codex 借鉴

  • run / turn / message / tool 四层事件模型（Thread/Turn/Item 的扁平化）
  • run() 返回 { text, messages, usage } 的 SDK 易用性标准
  • usage 分项统计（cached tokens 等）

从 dsh 继承

  • 「日志即事实」：追加式 JSONL、撕裂行容错、fork 复制历史
  • canonical transcript 与 transformContext 投影分离
  • turn（一次输入到停止）/ step（一次模型请求）术语体系

puck 原创

  • 目录级物理裁切（对照 dsh 的运行时插件卸载）
  • mock 剧本 provider：确定性离线复现多轮工具流
  • 计时观测：TTFT 入账 → 自包含 dashboard → LLM 合理性分析
  • <think> 内联思考流式剥离（真实接入 MiniMax-M3 时诞生）

一句话总结：Codex 赢在安全与规模，dsh 赢在生态与界面，pi 赢在库的完整与分层，puck 赢在极简、可裁切、可观测、可离线验证。它们不是竞争关系，而是一条谱系：从「产品」到「框架」到「积木」。
